# Non-document resource authoring

AH-704 adds and replaces one explicitly selected supporting resource through the public CLI. Markdown authoring remains the editable-body path. Resource bytes use the existing Notion Records exact-byte chunks; Files pages display ownership, path, immutable version and a retained-object entry. Their explanatory body is not the resource content.

AH-703/705/707 use the same effective tree and retained history for raw resources. A `resource_followed` baseline records exact source bytes, mode and source path; following reads still select the current fixed source. The recorded C2 baseline must not replace current C3 bytes or turn management notes into a native projection.

## Acceptance map

- `resource-bytes`: PNG, non-UTF-8 binary, JSON, CRLF scripts and empty files retain exact size/SHA256 and known executable mode. Reject an oversized or corrupt complete input before mutation; do not execute any submitted file.
- `resource-add`: explicit target/path/input, zero-write dry-run, one stable Files identity, owner relation and a verified immutable resource event. A fixed source path must use replace, never accidental add-over.
- `resource-replace`: keep an existing File ID or explicitly bind a previously source-only path; retain the prior exact bytes and immutable source identity. Append a version entry without overwriting the management page or another native body.
- `resource-original-operation`: freeze the plan before dispatch in the existing shared pending journal. Partial retention, unknown page creation, unknown version-entry append and unresolved event completion retain that exact operation. Reconciliation reads original facts only and sends no replacement write.
- `resource-consume`: ordinary CLI and SDK consume the same event/manifest/chunks. Resource management prose is never observed/adopted as file content. Read-only state and audit remain zero-write and distinguish remote verification from local cache availability.
- `resource-history`: a fresh isolated installed consumer reads both versions and restores the original pin after replacement. No token/state copying, global install, script execution or private fixture setters.
- `resource-mode`: known mode is optional snapshot/portable metadata and survives directory/ZIP export and historical restoration. Old pins without mode retain their exact identity; unknown historical mode is not guessed.
- `resource-move`: keep File ID, bytes and mode; update only the explicit Path property and retain the original source path. Reject occupied paths and broken current references. Unknown Path writes retain the original operation without appending an assumed completion or retrying the mutation.
- `resource-delete`: retain exact prior bytes, page and old complete pin before the tombstone. Later source updates cannot revive suppressed paths. `undelete` explicitly restores retained tombstone bytes as custom ownership, including resources with no upstream.
- `resource-restore`: select the exact current fixed source path, retain prior custom bytes, and publish raw following without a body overwrite. A missing exact source path fails; an already-following resource is an observed zero-write no-op. C1 → N1 → C2 restoration → C3 source advancement preserves each distinct state.
- `resource-scope`: explicit sharing of one input does not authorize uploading unrelated local-only files in a previous complete snapshot. Check durable content restrictions before both prepare and dispatch. Source restoration respects declared and materialized local scope.
- `mixed-pin`: manifest inspection does not claim local byte readiness; path-only materialization selects the requested original paths; complete remote restoration verifies all chunks. New consumers restore old custom/binary/mode combinations without current/latest substitution. A missing chunk fails even when a full-restore caller has warm local bytes.
- `cold-selected-resources`: a manager-verified Git SHA and a retained raw identity permit an empty consumer to return the complete directory without downloading unselected binary resources. Read one selected path, retain mode and raw hashes, then prove old-pin acquisition after the current resource changes. Legacy Git without SHA retains full acquisition; unknown SHA is not synthesized from Git OID. Full export and `--authoring` verify every effective byte.
- `cross-transport-reuse`: bytes previously read through another transport may satisfy a new fixed Git entry only after SHA-256, Git OID and length all agree; a corrupt object or inconsistent aliases fail before provider repair/publication.
- `bounded-observations`: real Node/SQLite processes keep one per-owner current file-observation slot. Higher reserved generations win, equal-generation conflicts fail, and cache clearing fences even a newer already-reserved request. Repeated fixed-version reads must report active row count and physical page/payload growth, independently of immutable history growth.
- `native-metadata-baseline`: a C1 custom main retains C1 frontmatter and known executable mode even after selecting C2. Known empty header stays empty; following resources use C2 bytes and mode together. Legacy unknown metadata is not guessed.

## Verification layers

Focused Core tests cover cryptographic framing, exact remote reads, file state transitions, dispatch recovery and composition. Public CLI tests cover explicit input selection, dry-run/schema/help and mode handling. Installed CLI/SDK acceptance records input/output byte hashes, the source/archive/bin identities, actual Notion requests and a separate empty-state readback. A controlled service does not establish real Notion acceptance; the owned live add and replace each require a distinct recorded readback.

The existing `scripts/package-smoke/authoring.ts` owns the installed raw lifecycle and independent empty SDK roots. It observes real installed SQLite original plans through a read-only oracle, rejects raw-management Markdown reads, reconciles a lost original outcome, compares old/new raw bytes and mode, and verifies the complete export. Run it through the normal package controller after the common build freeze; source tests alone do not pass this installed gate. `shared-sqlite.node.test.ts` exercises bounded cross-process generations and real Store partial snapshot publication; the memory fixtures do not substitute for those persistence checks.

Use the repository verification controller and preserve a fresh external evidence run. Do not alter production table schemas or hide unresolved operations to complete a test. The ordinary successful author command itself returns the verified original result; these extended evidence procedures are developer gates.
