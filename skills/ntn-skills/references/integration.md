# Discovery and integration

Use [the README](../../../README.md#quick-start) for prerequisites, installation and a first read. [The protocol](../../../docs/protocol.md) and [host adapter contract](../../../docs/host-integration.md) are the shared public references.

Install the built CLI package with npm and run it on Node.js 22.19.0 or newer. The host must put Node.js and `ntn-skills` on PATH; online operations also need the official `ntn` executable. Repository development/build/test tooling uses Bun separately.

Discover metadata before loading bodies. Read an actual current ref returned by `list`, require `ok: true`, and retain `content`, `ref`, `snapshot_id`, `version_id`, `source` and `freshness`. Ordinary content reads accept observations validated within five minutes (`source=local_cache`); `--refresh` validates current remote access/content (`source=notion`). Use `files <snapshot_id>` for every file in the fixed version and follow its pinned refs (`source=local_snapshot`). Pinned versions do not claim latest freshness. Inspecting, summarizing, editing or configuring a retained Skill does not activate its instructions; activate only the workflow selected for the task. No content or script executes automatically.

ntn-skills list follows all Search/row-query pages and returns databases/skills/count/coverage without bodies. Join Skill database_id to database title/alias/data_source_ids; Skill alias remains its invocation name. --query filters Skill Name/alias/Description and retains the full queried database map, including empty/no-match databases. --refresh bypasses the list cache. Discovery is limited to credential visibility and cannot prove workspace-wide completeness; preserve failed_sources database_id/alias/title/data_source_id. database list discovers database maps without querying Skill rows.

Discovery accepts native Skills databases and data sources with rich-text Description and References. References mode uses page Markdown; included page links become relative files under references/, with a path fixed by a `.md` link label or derived from the page title. Reference-only edits change the version. Optional Files preserves source bytes and other assets; without it main/reference Markdown exports are normalized. Host adapters retain the same command/ref interface for both modes. See [References pages](../../../docs/protocol.md#references-pages).

To query a known database directly:

```bash
ntn-skills source add frontend --database <database-id-or-url>
ntn-skills list --database frontend
```

All --database flags and config set-default accept one ID, URL or exact case-sensitive registered alias. IDs/URLs take priority; titles are display labels only. Repeated flags fail with INVALID_ARGUMENT/exit 2. Unknown aliases fail with DATABASE_NOT_FOUND; conflicting mappings fail with DATABASE_AMBIGUOUS; inaccessible selections never redirect. Pinned targets resolve aliases from local configuration and check snapshot ownership offline. Different databases may have the same Skill invocation name; retain both page identities and use the ambiguity error's databases map to select the domain or use a page-ID ref.

Source registrations are local, supplement discovery, and do not modify Notion. No custom Status filter is applied by default. Notion Name must use ASCII English letters separated by single spaces and be at most 64 characters. Lowercase it and replace spaces with hyphens to obtain the invocation name shown as the listed `alias`; the export's frontmatter `name` must match. Exact display titles and invocation names resolve only when one distinct page ID matches; case-only title differences can collide. Invalid titles return `INVALID_SKILL_NAME`, and mismatched export names return `INVALID_SKILL`. Descriptions and contents may use any language.

Source registrations and sync bindings live in config (`~/.config/ntn-skills/config.json`); immutable snapshots/objects, uploads, baselines/plans/receipts in state (`~/.local/state/ntn-skills`); disposable latest/catalog/selector observations in cache (`~/.cache/ntn-skills`). Override the complete roots with NTN_SKILLS_CONFIG_HOME, NTN_SKILLS_HOME and NTN_SKILLS_CACHE_HOME; XDG config/state/cache bases are also supported. Isolate all three for separate hosts. Legacy valid state config migrates only when new config is absent, retaining a `.migrated` backup. Upgrades preserve state/config and rebuild disposable indexes; old catalogs cannot manufacture freshness or initialize baselines.

The config may contain default_database. config set-default accepts the same ID/URL/alias selector, validates online and stores its canonical ID. Manage it through config show/clear-default. It applies to create/import only: --database wins, then the default, then the sole freshly discovered database. Name conflict/reuse/update is scoped to that database. Failed defaults and failed/ambiguous discovery never silently redirect writes.

Authentication selects non-empty config.token > NOTION_API_TOKEN > existing ntn login. Set a token through trusted piped stdin, never arguments/logs; clear-token restores fallback. Config operations preserve sources/defaults/policy/bindings and report token presence only. Tokens are plaintext with private permissions. Separate roots do not isolate official login; safe local credential/workspace/endpoint identity is required for eligible cached lookup. Official-login identity may need online validation; unpinned offline selection fails when scope cannot be determined safely. Pinned snapshots remain explicitly offline and older scopes remain readable; obtain a fresh current ref before writing from an older scope. [Scope contract](../../../docs/protocol.md#environment-and-local-storage).

`NTN_SKILLS_NTN_BIN` selects the trusted official CLI executable, default `ntn`. `NOTION_WORKSPACE_ID` and `NOTION_API_BASE_URL` enter the authentication scope and are inherited by `ntn`; workspace selection follows its authentication rules, while `ntn api` honors the API base URL override. Select a trusted endpoint because authenticated requests may reach it. Signed archive downloads follow the returned URLs independently. See [the environment contract](../../../docs/protocol.md#environment-and-local-storage).

The CLI sends no analytics requests of its own. Online operations use official `ntn` and signed download URLs; `ntn` has its own policies. Local access includes config/state/cache, explicit inputs and outputs. State's private immutable bytes, uploads and sync recovery have no automatic garbage collection. Content/catalog defaults are 5m/60s, configurable through set-cache-policy; TTL controls freshness, not retention. Cache status is offline and clear retires disposable observations through system Trash only. Uninstall retains all roots and pinned versions/recovery evidence. [Retention guidance](../../../docs/usage.md#upgrade-and-uninstall) and [security policy](../../../SECURITY.md).

For startup awareness, the host must inject list metadata or carry an instruction to use this bootstrap Skill for relevant tasks. A Skill description alone does not guarantee that the host already knows every remote workflow.

For direct Read tool support, the host must register a skill:// protocol adapter that invokes ntn-skills read with an argument array, parses JSON, preserves the snapshot, and propagates errors. If the host already owns skill:// for local skills, route explicitly instead of replacing its handler. Without an adapter, invoke the CLI through the shell tool.

Current read/open/files/export/list accept mutually exclusive `--refresh`, `--offline` or `--max-age DURATION`; expired ordinary reads validate or fail without stale fallback. Pinned snapshots and relative pinned --from reject refresh/max-age and permit redundant offline. Preserve JSON freshness; raw text omits it. Cached local content can remain after remote access revocation and is not proof of current permission. Never modify immutable cache/state objects directly.

For host Write integration, call `["write", uri, "--input", localFile]` as an argument array under current task authorization. Reuse the pinned read ref as the remote version baseline, propagate conflicts and partial/unknown outcomes, and adopt the new returned snapshot only after success. Never mutate cache objects or automatically retry an uncertain remote write. CLI support for skill:// writes does not register a host Write adapter.

For complete replacement, `import INPUT --target TARGET` selects an existing current page or pinned main-version baseline, preserves page ID on metadata rename, rejects reference-file targets and never falls back to create/name selection. Database constrains that target. Host synchronization registers a logical local path with sync bind, initializes differing/absent local content through an explicit sync plan --from notion|local, and applies only its saved plan ID/review copy after version/scope/base/hash/link checks. Plan --all checks shared-page candidates; status is provisional unless refreshed. Baselines advance only after verified convergence. Retain unresolved receipts and use sync reconcile without replay before another apply; unbind retains content/recovery. Logical links survive, retargeting invalidates plans, and filesystem checks are not atomic against external retargeting. Removed/replaced bytes require system Trash. [Sync workflow](../../../docs/usage.md#synchronizing-local-skills) and [authoritative protocol](../../../docs/protocol.md).

Adapters must tolerate additional JSON fields and propagate unfamiliar error codes as failures. Patch releases preserve current semantics; 0.x minor releases may break compatibility with documented migration steps. See [CONTRIBUTING](../../../CONTRIBUTING.md#compatibility-and-deprecation) and [the release procedure](../../../docs/releasing.md).
