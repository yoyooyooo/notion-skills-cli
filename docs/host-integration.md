# Host integration

Start with [installation and Quick start](../README.md#installation) before configuring a host. The 0.x series is experimental; [the compatibility policy](../CONTRIBUTING.md#compatibility-and-deprecation) and [changelog](../CHANGELOG.md) describe consumer expectations. This document defines an adapter contract, not a claim that adapters have been installed in other applications.

## Portable shell integration

The host needs Node.js 22.22.3+ within 22.x, or Node.js 24.20.0+ on PATH to launch the installed `ntn-skills` executable. Install the built package with npm using [the consumer installation instructions](../README.md#installation); online operations also need the official `ntn` CLI. Bun belongs to the repository's development/build path.

Context Broker exposes the three bundled Skills directly through ordinary `$` discovery. For a shell-only host using native local Skill discovery, expose the [entrypoint Skill](../skills/ntn-skills/SKILL.md) with `ctl builtin install notion/ntn-skills`: the CLI stores it centrally and links it into `~/.agents/skills` by default. Add `--agent-dir DIR` only for a host that needs another supported Skill root. A suitable default instruction is:

> When a task may benefit from the Notion Skill library, choose from its supplied metadata. If no remote catalog is supplied, use ntn-skills to discover it. Read only the selected workflow and keep supporting files on that version. Route Notion content changes to ntn-skills-maintain and source subscriptions and ongoing local-directory synchronization to ntn-skills-sync.

Default awareness is metadata and routing, not preloaded Skill bodies. The entrypoint calls `ntn-skills read skill://...` through a shell tool when no native adapter exists; it cannot register a protocol handler.

When enabled, the OMP/Pi Context Broker supplies a short `<ntn-skills-guidance>` block by default. It contains the resolved CLI argv, each enabled source's id and optional database, `list --query`, exact-ref `read`, pinned `files`/resource reads, local resource use and help entrypoints. Deduplication uses the effective context: repeat, fork and persisted continuation retain one copy; compaction or rewind that removes it restores it before the next model request, even without invoking a Skill. The guidance remains available with zero Notion sources and uses the package's resolved Node/CLI argv when no global CLI is installed. Custom CLI and multiple sources retain their own exact argv and database scopes; no source is implicitly selected merely because it is first. This guidance is independent of remote catalog discovery and selected workflow activation. The broker owns its implementation and [host lifecycle contract](https://github.com/yoyooyooo/pi-context-broker/blob/main/packages/context-broker/docs/reference.md#host-discovery-and-selected-activation).

The guidance includes per-source `list-args`, `read-args`, `files-args` and `resource-read-args` arrays carrying the configured database. Append one array to the executable argv and replace its placeholders. A successful read returns top-level `content`, pinned `ref` and `snapshot_id`; `record` is metadata. `files SNAPSHOT` lists resources and `read SNAPSHOT --path RELATIVE` reads a named file without a shell resolving a URI argument as a filesystem path. The CLI also supports relative `read RELATIVE --from PINNED_REF` where the host passes URI arguments literally. Complete bodies already supplied by the host/Broker or a successful read can be used directly for introductions and summaries. Resolve a requested relative file directly from a visible entry directory; read other supporting files only when needed. Retain JSON output to inspect CLI `ok`/`error` and snapshot identity. Inspection describes the workflow without running its setup or repository checks.

For selected Notion Skills, Broker payloads also provide pinned `skill-ref` and `snapshot-id`. When `hash` or `basename` path mode hides the local directory, use the supplied command and database scope with `files SNAPSHOT` or `read SNAPSHOT --path RELATIVE`. Skill introductions describe the workflow, style and prerequisites without executing or adopting them. A development host may use a public `ntn-skills` shim described in [Contributing](../CONTRIBUTING.md#development-setup); source paths belong to that shim rather than consumer prompts.

The three builtin IDs are `notion/ntn-skills` (discovery/consumption), `notion/ntn-skills-maintain` (Notion content changes) and `notion/ntn-skills-sync` (ongoing synchronization/recovery). Their supporting files are included, and each installs independently. Use `ctl builtin list/read` offline, `ctl builtin install ID`, `ctl builtin status [ID]` and `ctl builtin update ID` for centralized management. Optional repeated `--agent-dir DIR` adds distribution links at `DIR/skills/<name>` alongside the default shared link; all targets use the same installed tree. `ctl builtin export` remains an unregistered portable copy. See [usage](usage.md#optional-official-skills) for conflicts, migration and reload requirements.

Global configuration defaults to `~/.config/ntn-skills/config.json`; retained snapshots/recovery state to `~/.local/state/ntn-skills`; disposable observations to `~/.cache/ntn-skills`. Set `NTN_SKILLS_CONFIG_HOME`, `NTN_SKILLS_HOME` and `NTN_SKILLS_CACHE_HOME` to isolate all three complete application directories; XDG config/state/cache bases are also supported. Authentication selects config.token > non-empty NOTION_API_TOKEN > existing ntn login; a shared config token overrides a host's environment credential. Pass a token to `ctl config set-token --stdin` through a trusted stdin pipe, never arguments/logs. `ctl config clear-token` restores fallback; sanitized config reports token presence, not validity. Separate roots do not isolate official `ntn` login; where local login identity cannot be distinguished safely, current reads validate identity online and unpinned offline lookup fails. [Storage and scope contract](protocol.md#environment-and-local-storage).

`NTN_SKILLS_NTN_BIN` selects the official CLI executable (default `ntn`). `NOTION_WORKSPACE_ID` and `NOTION_API_BASE_URL` enter the authentication scope and are inherited by `ntn`; its authentication rules govern workspace selection, and `ntn api` honors the API base URL override. Use a trusted executable and endpoint, since authenticated API requests may reach that endpoint. Signed archive downloads follow the service's returned URLs independently. See [the environment contract](protocol.md#environment-and-local-storage).

`NTN_SKILLS_REQUEST_TIMEOUT_MS` sets each network attempt's timeout in milliseconds (default 30000). It covers each official Notion CLI request and each archive, attachment or source-provider HTTP download independently. A complete read has no aggregate deadline; cancellation still interrupts the active request and its owned process tree.

The CLI sends no analytics requests of its own. Online calls use official `ntn` and signed Notion downloads; `ntn` has its own policies. Local access covers configuration/state/cache, explicit inputs and requested outputs. Snapshots, upload staging, sync plans/baselines/receipts contain private bytes and have no automatic garbage collection. Content/catalog freshness defaults are five minutes/60 seconds and do not control retention. Uninstalling leaves all roots in place; preserve pinned versions and unfinished recovery receipts. Cache clearing retires only disposable SQL observations; it does not move files. [Cleanup guidance](usage.md#upgrade-and-uninstall) and [security policy](../SECURITY.md).

## Bundled Skills in hosts

OMP/Pi and Tern expose package Skills through the same ordinary `$` selection path as other Skills:

| Task | Exact package selection |
| --- | --- |
| Discover and consume the library | `$ntn-skills@builtin` |
| Create or change Notion content | `$ntn-skills-maintain@builtin` |
| Connect and synchronize source/local content | `$ntn-skills-sync@builtin` |

The explicit `@builtin` suffix selects package identity even when a local directory or Notion page has the same name. Builtin instructions and supporting references work offline with no configured Notion source or global `ntn-skills` installation. The broker supplies its bundled CLI argv for content work; remote operations still need an existing Notion connection. Reading or previewing a Skill does not activate its instructions until it is selected for the task.

Pi/OMP use ordinary `$` discovery and loading. Tern's automatic menu is owned by the Broker; a manual selection inserts the exact token into the existing composer. `/context-broker` controls session status, source/View selection and refresh. The former `/ntn-skills` management/save commands and separate CLI/schema palettes are removed. Content maintenance is expressed as a task for the selected builtin, which uses the public CLI command surface.

Independent local installation remains available through ordinary `ctl builtin install/status/update/export` commands for native hosts or explicitly managed copies. It uses the central XDG data tree and registered distribution links described in the [local contract](protocol.md#official-built-in-skills). Package builtins, managed local copies and remote Notion copies retain separate identities and versions. Reload or restart native host discovery after updating a managed local copy; OMP uses `/restart` when extension code itself changes.

## Startup metadata integration

Startup discovery runs unfiltered `ntn-skills list` for the complete explicit-selection catalog, retaining name/description/ID/alias/ref metadata, databases, `source`, `freshness`, `fetched_at` and `coverage`. Separately, the selected View determines which entries are advertised to the model before its first user-triggered request; the full catalog is not automatically injected. Join database_id to title/domain alias; keep these separate from invocation alias. List paginates without bodies/manifests; `--query` retains the full queried database map. Catalog default age is 60 seconds; use `--refresh` for fresh discovery or intentional `--offline` for cached discovery. Preserve failed_sources identities and incomplete/search-limited coverage. Hosts retain both same-alias pages across databases and select by database scope/page-ID ref rather than a name-only map.

Cold catalog discovery validates subscription Router membership against the complete current metadata inventories already queried for the selected content databases and subscription source. It does not refetch each Router's member pages or read bodies merely to populate completion. Missing or conflicting member metadata remains a coverage failure. Selecting a Router still freshly validates its active map and members; a cached directory does not authorize activation.

Only automatic subscription Routers with at least two verified published active Skills appear in the catalog. Zero/single-member subscriptions preserve independent Skill records and upstream display labels; they do not produce Router completion candidates. Current exact Router activation enforces the same minimum. Manually authored content-table Routers keep their explicit membership behavior. Upgrades invalidate old CLI catalogs and subscription Router observations; refresh the host catalog rather than retaining an obsolete candidate. Pinned snapshots remain immutable historical reads.

Online subscription activation queries fresh member metadata from every target data source, filtered by the publisher relation and fully paginated. It validates each active member's exact database/data-source parent, ownership, key, published hash and committed marker, then reuses those validated rows when materializing the Router snapshot. Missing members, inaccessible queries and missing or repeating pagination cursors fail the read.

Each listed `name` is the exact human-readable Notion display title; authored frontmatter `name` retains its original spelling. Names must be nonempty and contain no control characters; Unicode, digits, spaces and hyphens are allowed. The separate callable `alias` uses NFC normalization and lowercase, trims surrounding whitespace, replaces whitespace runs with `-`, and percent-encodes characters outside Unicode letters, marks, numbers, `_` and `-`. For example, `Tty7` stays `Tty7` with alias `tty7`, and `Review/2026` has alias `review%2F2026`. Use the alias for host invocation while preserving the display title and source frontmatter. Aliases never identify records: retain collisions and select exact page IDs or refs. References mode generates frontmatter from the exact title; native exports need not match the alias or directory. Propagate `INVALID_SKILL_NAME` and `INVALID_SKILL` for malformed content.

The OMP/Pi adapter contract selects default discovery from a Notion View. The host chooses a session override, then source `default_view_id`, then the first View in API order. Use `views --database SELECTOR`, `list --view VIEW_ID_OR_URL` or `list --default-view --database SELECTOR`. View membership has no extra `default_context` intersection; that boolean remains ordinary page metadata. Keep unfiltered `list` for full `$` invocation, search and exact reads. An invalid explicit/default ID is reported without fallback; verified zero Views gives an empty default directory. Startup prepares metadata and optional snapshots without provider calls or body activation. `before_agent_start` supplies one current metadata directory before the first and subsequent user-triggered requests. A View switch replaces only Broker-owned metadata for the next request, preserving unrelated local Skills and loaded snapshots. Session overrides follow active-branch entries across resume/fork and do not mutate configuration. Preparation remains distinct from loaded context; Prompt is never default-discovered or prefetched.

On activation, call `ntn-skills read <ref>` with an actual current ref returned by list. Require `ok: true` and retain `content`, `source`, `freshness`, pinned `ref`, `snapshot_id` and `version_id`. Ordinary reads may select content validated within five minutes (`source=local_cache`); use `--refresh` when activation requires current remote access/content (`source=notion`). Hosts must preserve the observation time/age/limit/stale status, not infer freshness from snapshot creation. Once selected, the complete snapshot fixes supporting instructions for the task. List all files with `["files", snapshot_id]` and follow pinned refs (`source=local_snapshot`); pinned versions do not claim latest freshness. Inspecting, summarizing, editing or configuring a Skill does not activate its instructions. Downloaded contents/scripts never execute automatically. [Read walkthrough](usage.md#reading-a-fixed-version).

Preserve optional `freshness.validation="metadata"`: ordinary current Skill reads can revalidate an already aligned source-bundle checkpoint using root/reference metadata, full References membership and immutable attachment identity, then reuse the local file set. `source=notion` can therefore describe remote metadata validation rather than new body downloads. This is a cache validator and can miss edits with unchanged reported versions. `--refresh` or explicit `--max-age 0` forces complete body/resource validation; mutations and synchronization retain strong reads. A cold machine without a checkpoint validates fully, and permission errors never become stale success.


All --database flags accept one ID, URL or exact case-sensitive registered alias. Register domains with ctl database register frontend --database DATABASE_ID, then invoke ["read", name, "--database", "frontend"]. Database titles are display labels only. Repeated --database values return INVALID_ARGUMENT before online access/mutation. ctl config set default_database accepts the same selector but stores its ID and affects create only. ctl database unregister frontend removes only that local alias offline. Pinned requests with an alias constraint resolve it locally and enforce cached database ownership. See [database selection](protocol.md#identity-and-references).

Databases with rich-text Description and References are discoverable alongside native Skills databases. References mode reads page Markdown, materializes included pages under references/, and rewrites Notion page links relative to the containing file. The version includes every reference page, so child-only edits can cause WRITE_CONFLICT. Host adapters use the same commands and pinned refs for either storage mode. See [References pages](protocol.md#references-pages).

References materialization restores local Markdown block boundaries around tables, fenced code and paragraphs after lists, and joins split emphasis around inline code. Snapshot identities include the materialization version; existing pinned snapshots remain immutable, so hosts must activate a current version to receive changed materialization. Automatic import verification covers saved instructions, code languages and source bytes; it does not establish host reload or workflow execution.

## Broker source consumption

`pi-context-broker` provides a one-way Notion source adapter in its own repository against these public commands, including host registration, selected-View background preparation and selected-page read/export. Installation, host configuration and verification belong to that broker repository; this CLI package does not install the adapter or establish that it is installed in a user's host. The CLI owns metadata, credential scopes and immutable export bytes; the broker owns its source index, host registration and activation policy. No CLI-side broker-specific API or remote write is required.

Discover with an argument array such as `["list", "--database", databaseSelector]`. Keep `scope`, `fetched_at`, `source`, `freshness`, the database map and the complete `coverage` object, including `failed_sources`. Rows contain page IDs and current refs without bodies or file manifests. Key records by source ID plus page ID; preserve same-name rows across databases and scopes. A metadata index alone is insufficient for executing a workflow.

Consumers may call `["ctl", "cache", "identity", "--database", databaseSelector]` before selecting their persisted metadata index; omit `--database` for unscoped discovery. The response supplies an opaque credential/remote-catalog identity and `catalog_max_age_ms` without network access or credential output. The CLI resolves database aliases, IDs and URLs locally. Share one index for that identity across projects and Pi/OMP; working directory, executable spelling, host/source labels and cache policy do not define different Notion content. Recompute list age from its original `freshness.validated_at` under the current discovery policy; process startup must not reset TTL. A host may display expired metadata while refreshing, but selected activation still validates scope and the fixed snapshot. If a custom command lacks this optional capability, use its normal list contract. [Cache identity contract](protocol.md#read-policy-and-cache-management).

The database map records content and upstream roles separately. Validate each locator against its exact database/data-source pair and `coverage.queried_data_sources`: content pages require a content source, subscription Routers require an upstream source. A selected content database constrains a subscription's `target_database_id`, not its upstream locator. Keep source ID, namespace and scope attached through registration and exact-ref activation; incomplete coverage remains a source failure. Successful explicit reads alone do not demonstrate catalog discovery.

When the user selects a workflow, invoke `["read", pageId, "--database", databaseSelector]`. Require a successful exit and `ok: true`; compare the returned `scope` with the discovery scope before associating instructions with that record. A scope change requires rediscovery. Retain the returned page, version and snapshot IDs plus the pinned ref and freshness; online validation failures remain failures rather than empty instructions. Current read scope identifies the selected credential observation, whereas pinned read scope identifies the original snapshot and does not prove present permission.

Materialize that fixed version with `["export", snapshotId, "--projection", "snapshot", "--format", "directory", "--output", ownedSnapshotDirectory]`. Explicit snapshot selection is offline and never changes Notion. Require `projection:"snapshot"`; match response `main_path` and `entrypoint` to portable v2 `.ntn-skills.json`'s `main` and the selected record's dynamic entrypoint. Do not assume `SKILL.md`: kind and entrypoint belong to the selected record. Require complete entry bytes equal to `read.content`, including a Router's generated Members index. Verify every receipt file's `path`, `bytes`, SHA-256 `hash` and `role` (`entrypoint`, `resource`, `source_bundle`, `manifest`) against the complete exported tree. Preserve its containing directory and all relative resources. The manifest contains format, version 2, kind, name, description and main, but excludes page/version/snapshot IDs and scope; retain those response identities separately. Default `--projection source` preserves authored portable bytes and can differ from the read view.

Repeat an export to identical output to receive `reused: true`; differing output returns `OUTPUT_CONFLICT` without overwrite. Consumers must retain that error rather than replacing the directory silently. Spawn the installed `ntn-skills` executable or its declared Node.js bin using argument arrays. Isolate config/state/cache roots per intended credential scope and never store tokens in broker source configuration. A saved CLI token takes precedence over the environment, so separate roots alone are insufficient if personal configuration is copied in. Unpinned offline lookup cannot reuse another credential scope; explicit pinned snapshots remain locally readable without credentials.

Repository verification provides a read-only `consumption` mode and installed npm consumer smoke. They cover the CLI boundary only; broker default-catalog, Read interception and native skill commands require separate broker-host evidence. Verification recipes are repository-only and are not shipped or advertised as an installed host integration.

## Built-in Read protocol integration

An adapter implements the host's URI dispatch contract:

1. Accept only `skill://` requests owned by this adapter. A host already using this scheme must make routing explicit; do not override its existing local skill handler.
2. Invoke the executable with an argument array: `["read", uri]`. No shell interpolation.
3. Parse stdout as JSON and honor both `ok` and exit status.
4. Return `content`, `path`, `ref`, `snapshot_id`, `version_id`, `source`, `freshness`, `range`, and `has_more` to the Agent. Accept additional JSON fields and propagate unfamiliar error codes as failures.
5. Persist the returned snapshot in the host's activation state. Subsequent relative reads must use pinned refs or pass `--from` with the pinned containing-file ref.
6. Forward errors as tool failures, including candidate IDs and coverage. Never turn errors into an empty skill document.
7. Handle binary assets through --output and a host viewer. Identical existing bytes return reused=true; differing output fails with OUTPUT_CONFLICT. Never execute imported scripts automatically.

The CLI accepts `--lines` to implement ranged text reads, and `resolve` to preserve versions while resolving relative references. An adapter should not reimplement name matching or path normalization.

An adapter may expose one of `--refresh`, `--offline` or `--max-age DURATION` for a current target; the flags are mutually exclusive. Pinned targets or pinned relative `--from` reject refresh/max-age and permit redundant offline. Failed online validation never silently falls back to stale content. A cached observation does not prove current permission; use JSON for freshness metadata rather than raw text. [Read-policy usage](usage.md#reading-a-fixed-version).

## Explicit write integration

For an authorized file/metadata change, invoke `["apply", pinnedMainRef, "--input", changedFolder]`, adding only requested `--remove`, `--name`, `--description` or other property flags. The sparse input contains only added/changed files; omitted files remain intact. The CLI assembles one complete change from the pinned baseline and returns its verified snapshot and original publication operation ID. Adopt the new snapshot explicitly for subsequent work while existing activations retain their old version. A host's single-file Write tool may use `["write", pinnedFileRef, "--input", localFile]`. Never route writes into immutable local snapshot objects.

`write` changes only the selected logical file. Read-view or submitted frontmatter is file content and never changes Name, Description or Default Context. For authorized property changes, invoke `["update", exactTarget, "--name", title]`, adding only requested `--description` or `--default-context true|false` flags; retain a pinned baseline and propagate version/property conflicts. Create is create-only and rejects an existing name; use exact-target replace for intentional whole-content replacement.

Use `--dry-run` to report a concrete target/action. Propagate conflicts and partial/unknown results without automatic retries. Create chooses explicit database > configured default > sole fresh discovery. Inputs are ZIP/folder/Markdown; `--name` explicitly overrides the human title without changing page identity or rewriting authored frontmatter to an alias, while `--description` overrides Description. `replace INPUT --target EXACT` requires a page ID/URL, page-ID main ref or snapshot ID, preserves page ID through rename and fails without create/name fallback; database is a constraint. Names and reference-file targets cannot select replacement. References become editable pages; omitted references remain in Notion. Files preserves original bytes/frontmatter/assets; page-only output is normalized. Success returns verified snapshot metadata. [Mutation contract](protocol.md#mutation-contract).

Authorized publication commands can add `--progress`; drain stderr separately for stage/timing JSONL while parsing one final stdout JSON result. Preserve `operation_id` and the state-relative `receipt_path`. Invoke `["operation", "resume", operationId, "--progress"]` to revalidate and continue frozen input on the same target. Surface conflicts and unresolved outcomes for inspection; do not reconstruct a new create/replace from the display name. [Publication recovery contract](protocol.md#mutation-contract).

Completed recovery replays the retained result, including a single-file write's `path`, target-file `ref` and original `previous_version_id`; do not substitute the main-file ref. Validation reads are provisional until their complete checks pass, and checkpoint/continuation reads reject changed retained observations after a process exit.

For portable output, invoke `["export", selector, "--output", localPath]`, optionally with `--format zip|directory`. Pinned selection is offline; current selection uses bounded content policy, with `--refresh` for fresh remote validation. Preserve `.ntn-skills.json` for reimport. Identical destinations return `reused=true`; differing destinations fail with `OUTPUT_CONFLICT`. Export never mutates Notion. [Portable contract](protocol.md#portable-export-contract).

## Explicit local synchronization

Source subscription integration uses `["sync", "upstream", leaf, ...args]`; discover its official schema with `["schema", "sync", "upstream", leaf]`. The root `upstream` path is removed. `sync upstream run` requires exactly one mode: repeatable `--target SUBSCRIPTION_ID` or `--all`. Preserve exact subscription IDs, frozen plan IDs and durable operation IDs in host actions and recovery flows.

Start a Git subscription with `["sync", "upstream", "connect", source, "--database", databaseSelector]`, then invoke `run --target SUBSCRIPTION_ID` for recurring updates. A run continues an original pending publication before a fresh plan. It can restore a still-selected tracked member only when the exact owned original page is readable and confirmed in Notion Trash. Missing permission or a failed read remains a failure. Preserve returned subscription, original operation and restored member identities; do not direct routine recovery to historical operator commands.

Connect a logical distribution directory with `["sync", "local", "connect", pageId, "--path", directory, "--as", label]`, then use `sync local run LABEL` or `run --all`. An absent ordinary local directory initializes from Notion; existing differing content requires an explicit `--from notion|local`. Run settles only verifiably converged retained effects and preserves unresolved operations without replaying content writes. Separate `plan LABEL --output FILE` and `apply --plan FILE` remain available when a reviewed artifact is required, with the original binding, digest, scope/version, baseline, hashes and link checks.

`sync local status` is local/provisional unless refreshed; it cannot activate or advance a baseline. Baselines advance only after verified convergence. Preserve operation receipts on interruptions; `operation reconcile OPERATION_ID` reads actual outcomes without replay, and affected resources stay fenced while outcome is unresolved. Logical directory/parent/per-file links survive writes to final destinations; link drift rejects a saved plan. Commit-boundary guards do not supply an atomic guarantee against external link retargeting. Removed/replaced bytes require system Trash retention. `sync local unbind LABEL` deactivates configuration while retaining content/baselines/plans/receipts. [Workflow and limits](usage.md#synchronizing-local-skills).

Expose offline `ctl cache status` for effective roots/observations and `ctl cache clear TARGET [--database SELECTOR]` or `ctl cache clear --all` with optional `--dry-run`. Clear retires only disposable SQL observations; immutable versions and sync state remain. `ctl config set cache_policy.read_max_age_ms 300000` and `ctl config set cache_policy.catalog_max_age_ms 60000` control defaults in integer milliseconds. `ctl config unset KEY` restores the selected cache default while preserving authentication/sources/bindings and the sibling cache setting. [Cache usage](usage.md#cache-policy-and-cleanup).
